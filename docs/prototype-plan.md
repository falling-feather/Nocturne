## 1. 产品目标

FeatherNote 解决两类高频场景：一是在游戏或创作过程中，用全局快捷键立刻记下短想法；二是在主窗口中整理富文本笔记、概念图与日常待办。产品坚持本地优先、低打扰和快速响应，不以浏览器内核或在线账号作为基本依赖。

本轮原型验证以下问题：

1. C++/Qt Widgets 桌面程序能否满足常驻、快速呼出和较小资源占用的目标。
2. SQLite 是否足以可靠保存笔记、快速便签和待办。
3. 富文本、图片与轻量文档交换能否覆盖游戏灵感记录的核心流程。
4. 哪些 Qt 成本真实存在，哪些需求值得在后续用纯 Win32 重写。

## 2. 技术方案

### 2.1 当前技术栈

| 层次 | 选择 | 当前用途 |
| --- | --- | --- |
| 语言 | C++17 | 应用逻辑与平台接入 |
| UI | Qt 6 Widgets | 主窗口、编辑器、便签、待办和托盘 |
| 本地数据库 | Qt SQL + SQLite | 笔记、待办与快速便签持久化 |
| Windows 接入 | Win32 `user32` | 全局快捷键相关能力 |
| 构建 | CMake + Ninja | UCRT64 Release 构建 |
| 部署 | 自带 PowerShell 打包脚本 | 选择 Qt 插件并递归收集 UCRT64 运行依赖 |

开发机已知工具链为 `D:/msys64/ucrt64`，Qt 版本为 `6.10.1`；`CMakeLists.txt` 的最低 Qt 要求为 `6.5`。

### 2.2 模块边界

```text
src/main.cpp
  ├─ 单实例锁、应用元数据与数据库初始化
  ├─ Database
  │    ├─ notes：笔记正文与软删除状态
  │    ├─ todos：待办与完成状态
  │    └─ settings：quick_note 等小型设置
  └─ MainWindow
       ├─ NoteEditor：富文本与图片粘贴/拖入入口
       ├─ StickyNoteWindow：快速便签窗口
       ├─ 系统托盘
       └─ Ctrl+Alt+N 全局快捷键
```

当前数据库启用 SQLite WAL 与 `busy_timeout`。这可以改善本地写入的可用性，但不等于已经具备跨进程协作或在线备份能力；应用仍采用单实例策略。

## 3. 当前原型功能

### 3.1 主笔记

- 新建笔记并在列表中切换。
- 按标题或正文纯文本搜索。
- 编辑标题与正文；编辑变化在约 `650 ms` 无新输入后触发自动保存。
- 删除笔记时写入软删除状态，不在 UI 中提供回收站或恢复入口。
- 编辑器支持撤销与重做。

### 3.2 富文本与图片

- 粗体、斜体、下划线、标题、正文样式、项目符号列表、编号列表、字号与文字颜色。
- 从剪贴板粘贴图片。
- 将 PNG、JPEG、BMP、GIF 或 WebP 本地图片拖入编辑器。
- 通过文件选择器插入图片。
- 图片最长边超过 `1800 px` 时按比例缩小，再以带 UUID 的 PNG 文件写入本地 `attachments` 目录；笔记 HTML 保存其本地文件引用。

原型已经实现最小附件外置，但稳定命名、去重、迁移、孤儿清理和备份完整性尚未形成正式兼容契约，见[9.2 附件外置](#92-附件外置)。

### 3.3 文档交换

当前提供 HTML、Markdown 与纯文本的导入/导出入口。它们用于轻量交换，不承诺富文本、HTML 和 Markdown 之间完全无损往返：字体、颜色、复杂嵌套列表、表格或不受支持的 HTML/CSS 可能被简化。

DOCX 不属于本轮原型能力，见[9.4 DOCX](#94-docx)。

### 3.4 快速便签、待办与托盘

- `Ctrl+Alt+N` 在应用驻留时呼出置顶的快速便签。
- 快速便签内容保存在数据库 `settings` 表的 `quick_note` 键中。
- 待办支持新增、完成/未完成切换与清理已完成项目。
- 关闭主窗口转为托盘驻留；托盘用于重新打开主窗口、呼出便签或完全退出。

当前待办不包含到期提醒、重复规则、通知中心集成或日历同步。

## 4. 交互约定

### 4.1 快捷键

固定原型快捷键为 `Ctrl+Alt+N`。预期行为是：

1. FeatherNote 已在运行时，快捷键显示并聚焦快速便签。
2. 快速便签已显示时，再次触发仍应把窗口带到前台，不应创建无上限的新窗口。
3. 快捷键被其他程序占用时，应用应保持可用，用户仍可从主窗口或托盘打开便签。

快捷键尚不可在设置中修改，这是原型边界。

### 4.2 关闭与退出

窗口右上角的关闭操作只隐藏主窗口并保持托盘驻留，因此数据库和全局快捷键仍在使用。进行备份、替换数据库或更新程序前，必须从托盘菜单完全退出，并确认 `FeatherNote.exe` 进程已经结束。

### 4.3 自动保存

自动保存采用约 `650 ms` 防抖，目标是在连续输入时减少磁盘写入。自动保存不是备份：误删、错误导入或数据库损坏仍可能同步写入当前数据，因此需要独立副本。

## 5. 数据与安全

### 5.1 数据位置

`Database` 使用 `QStandardPaths::AppLocalDataLocation`。按当前应用元数据，Windows 上典型路径为：

```text
%LOCALAPPDATA%\FeatherNote\FeatherNote\
├─ notebook.sqlite3
└─ attachments\          # 原型插入图片的 PNG 文件
```

最终位置应以 Qt 在运行电脑上解析出的路径为准。SQLite 采用 WAL 模式，程序运行时同目录可能出现 `notebook.sqlite3-wal` 和 `notebook.sqlite3-shm`。

### 5.2 数据结构

| 表 | 当前职责 | 关键内容 |
| --- | --- | --- |
| `notes` | 主笔记 | 标题、HTML、正文纯文本、创建/更新时间、软删除状态 |
| `todos` | 待办 | 文本、完成状态、到期字段、排序字段 |
| `settings` | 小型设置 | `quick_note` 键值等 |

数据库内部存在到期与排序字段，不代表当前 UI 已提供完整的到期提醒或拖拽排序功能。

### 5.3 备份要求

当前没有自动备份。安全的手动备份顺序是：

1. 从托盘完全退出 FeatherNote。
2. 确认 `FeatherNote.exe` 进程不存在。
3. 复制整个 `AppLocalDataLocation` 数据目录，而不是只复制 `notebook.sqlite3`。
4. 在备份目录中保留时间戳，并至少保留一份位于另一块磁盘或可信同步介质上的副本。
5. 恢复前先备份当前目录，再替换为一份完整旧副本；恢复后检查笔记、图片和待办。

可直接使用根目录 [README 的 PowerShell 备份示例](../README.md#数据与备份)。备份内容当前未加密；如果笔记含敏感资料，必须使用受信任的加密磁盘或加密归档保存副本。

## 6. 构建与发布

### 6.1 Release 构建

在仓库根目录的 PowerShell 中执行：

```powershell
.\build.ps1 -Configuration Release
```

预期输出入口是 `%LOCALAPPDATA%\FeatherNotePrototypeBuild\Release\FeatherNote.exe`。中间目录刻意位于纯英文路径，规避 MSYS2 Qt `moc` 在部分 Windows 区域设置下无法向中文路径写中间文件的问题。脚本默认同时运行 CTest；性能验收必须使用 Release 构建。

### 6.2 运行与部署

开发机运行：

```powershell
& "$env:LOCALAPPDATA\FeatherNotePrototypeBuild\Release\FeatherNote.exe"
```

分发测试前运行 `.\build.ps1 -Configuration Release -Package`。MSYS2 的 `windeployqt` 本轮未完整复制非 Qt 依赖，所以 `scripts/package.ps1` 会递归调用 `ldd`，只收集所选 EXE、Qt DLL 与插件真正引用的 `/ucrt64/bin` DLL。完整命令见 [README 的打包可测试目录](../README.md#打包可测试目录)。发布检查至少包含：

- `platforms/qwindows.dll` 存在。
- SQLite 驱动插件随包存在。
- UCRT64/MinGW 编译器运行库随包存在。
- 在不依赖开发机 Qt `PATH` 的环境中可以启动、保存并重启读取笔记。

## 7. 原型边界

| 范围 | 当前结论 |
| --- | --- |
| 操作系统 | 仅 Windows；未做 macOS/Linux 适配 |
| 数据保护 | 本地 SQLite、WAL、软删除；无自动备份、加密或恢复 UI |
| 同步与账号 | 不支持云同步、多人协作和账号系统 |
| 快速便签 | 单一快速记录入口；无多便签管理、钉选层级或显示器规则承诺 |
| 待办 | 基础新增与完成；无提醒、重复、日历或优先级完整交互 |
| 文档兼容 | HTML/Markdown/TXT 轻量交换；非完全无损；无 DOCX |
| 图片 | 已初步外置为 PNG；正式附件生命周期与跨设备可移植性未定稿 |
| 数据迁移 | `0.1.0` 原型 schema 不构成后续版本兼容承诺 |
| 性能 | 已有一次短时资源快照；内存与包体超过目标，尚未完成正式长时基准 |

原型不应保存唯一副本的重要资料。测试数据进入后，不应在程序运行期间直接编辑数据库文件，也不应把 `-wal` 或 `-shm` 文件当作可随意删除的缓存。

## 8. 性能验收目标

### 8.1 目标与实测分栏

目标仍需按统一基准机正式验证。本轮只记录开发机上的短时快照，不能替代 10 分钟稳定性、P95 或大型游戏共存测试。

| 指标 | 原型验收目标 | 测量口径 | 当前实测 |
| --- | --- | --- | --- |
| 冷启动 | 主窗口可交互 P95 不高于 `600 ms` | Release、NVMe、本地数据库、连续 10 次冷启动 | 待测；仅验证可独立启动 |
| 快捷呼出 | 驻留进程中便签可输入 P95 不高于 `150 ms` | 主窗口隐藏，连续触发 30 次 `Ctrl+Alt+N` | 功能通过；延迟未采集 |
| 空闲 CPU | 10 分钟平均不高于单核等效 `0.2%` | 主窗口隐藏、无输入、无搜索 | 短样本：10 秒累计 `0.1406` CPU 秒；约全机 `0.064%`（22 逻辑处理器），口径不足以验收 |
| 空闲内存 | 稳定工作集不高于 `60 MiB` | 启动后使用 10 分钟，再隐藏并等待 5 分钟 | 短样本：工作集 `102.9 MiB`、私有 `78.4 MiB`；当前不达目标 |
| 自动保存卡顿 | `1 MiB` 纯文本笔记保存 P95 不高于 `50 ms` | 关闭其他写入，记录 100 次提交耗时 | 待测；本轮尚未采集 |
| 搜索响应 | `2,000` 条短笔记查询 P95 不高于 `100 ms` | 固定数据库，30 个查询词 | 待测；本轮尚未采集 |
| 部署体积 | 便携目录不高于 `70 MiB` | Release、无翻译、包含编译器运行库 | `36` 文件、`75.9 MiB`；当前不达目标 |

### 8.2 验收方法

1. 固定一台基准机，记录 CPU、内存、磁盘、Windows 版本和电源模式。
2. 使用 Release 包，并在测试记录中写出 Git 提交或源码快照标识。
3. 分别测试空数据库、普通数据集和压力数据集；普通数据集至少包含文字、图片和待办。
4. 每项报告样本数、中位数、P95 和最差值；不得用单次最好结果代替验收结果。
5. 同时运行目标大型游戏做一次共存观察，记录 FeatherNote 的工作集、CPU、快捷键延迟以及是否发生焦点抢占。
6. 将真正测得的数字写入上表“当前实测”，并附测试日期与环境；未测项保持“待测”。

如果 Qt 原型未达到某项指标，应先用分析工具确认启动、插件加载、绘制、数据库或图片处理中的真实瓶颈，再决定是否以纯 Win32 重写。

## 9. 后续路线

### 9.1 纯 Win32 可行性

目标不是为了技术偏好立即推翻原型，而是用实测判断 Qt 运行库、启动和常驻开销是否超出产品预算。候选方向是保留可复用的 C++ 数据/领域层，以 Win32 窗口、DirectWrite 与 Direct2D 替代 Qt Widgets UI；全局快捷键、托盘和单实例继续使用 Windows 原生 API。

进入重写前必须完成：

- 建立 Qt Release 基线，定位真实内存和启动成本。
- 把数据库与 UI 解耦，并为数据读写建立回归测试。
- 做最小 Win32 便签样机，对同一台机器、同一测试口径进行 A/B 比较。
- 只有收益覆盖开发复杂度、无障碍、输入法、高 DPI 和富文本成本时，才决定迁移。

### 9.2 附件外置

原型已经把插入图片作为数据库之外的 PNG 文件保存，并在笔记 HTML 中保留本地文件引用。后续计划把这项最小实现升级为有稳定兼容契约的附件系统，在数据库中维护引用与元数据。设计需要覆盖：

- 基于内容哈希或稳定 ID 的文件命名与去重。
- 图片格式、大小、校验值、原始文件名和归属笔记元数据。
- 相对引用与数据目录整体搬迁，不依赖开发机绝对路径。
- 删除笔记后的延迟垃圾回收、孤儿扫描和误删恢复窗口。
- 数据库与附件的一致性备份、恢复校验和缺失文件提示。

当前图片实现可用于体验，不应在上述规则落地前视为长期兼容格式。

### 9.3 Markdown

后续需要明确 Markdown 是交换格式还是笔记的规范存储格式。计划以 CommonMark/GFM 兼容子集为基线，为标题、列表、代码块、链接和本地图片建立往返测试；不支持的富文本样式必须给出降级规则，而不是静默承诺无损。

编辑体验可以继续采用富文本视图，但应提供源码预览或明确的导出结果预览。附件外置后，Markdown 图片链接使用可搬迁的相对路径。

### 9.4 DOCX

DOCX 计划作为可选导入/导出适配器，不让 Word 自动化或大型文档引擎成为常驻核心依赖。第一阶段只承诺段落、标题、粗斜体、基础列表和图片；表格、页眉页脚、批注、修订与复杂版式应检测并提示可能降级。

实施前需要比较轻量转换库、外部一次性转换进程和系统已有 Word 能力的体积、安全与许可证成本。任何方案都必须在测试文档集上验证，不得仅以“文件可打开”作为兼容完成标准。

### 9.5 数据可靠性与产品化

- 自动滚动备份与可视化恢复，默认保留多代并校验数据库完整性。
- schema 版本与可回滚迁移，不再直接修改原型表结构。
- 回收站、软删除恢复与附件一致性清理。
- 可配置快捷键、冲突提示、多显示器和高 DPI 验证。
- 待办提醒是否进入核心需结合常驻唤醒与资源预算评估。
